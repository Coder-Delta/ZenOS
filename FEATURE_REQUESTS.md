# Feature Requests

Feature requests are welcome.

ZenOS is an experimental project, so new ideas can help shape the system's architecture and capabilities.

## Before Requesting a Feature

Check:

* Existing issues
* Existing Pull Requests
* Project documentation
* Current roadmap, if available

The feature may already be planned or implemented.

## Good Feature Requests

A useful request explains:

* The problem
* The proposed solution
* Why it is useful
* Possible implementation
* Alternatives considered
* Potential drawbacks

## Feature Request Template

```text
## Feature

Short name of the feature.

## Problem

What problem does this solve?

## Proposed Solution

Describe your proposed implementation.

## Alternatives

What alternatives did you consider?

## Impact

Which parts of ZenOS would this affect?

- Kernel
- Init
- Root filesystem
- Userspace
- Networking
- Security
- Build system
- Documentation
- Other

## Additional Information

Add diagrams, examples, or references if useful.
```

## Large Features

Large architectural features should be discussed before implementation.

Examples:

* New init system
* Package manager
* New boot architecture
* Networking subsystem
* Security framework
* AI integration
* New userspace architecture

## Experimental Features

Experimental features are welcome when they are clearly identified and isolated from stable functionality.

Experimental implementations should include documentation describing:

* Current status
* Known limitations
* Testing method
* Future work

## Feature Scope

Not every feature request will be implemented.

The maintainers may consider:

* Technical feasibility
* Maintenance cost
* Security implications
* Compatibility
* Project direction
* Available contributors
